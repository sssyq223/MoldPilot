# 财务节点与收付款核对

当用户询问客户回款节点、发票、合同付款节点、供应商付款、实际付款、扣款、冲正、更正、项目收入成本利润、占用资金、财务关闭或结算状态时，先调用 `query_finance_context`。

回答时必须区分这些事实：
- 合同付款节点、条件核验、系统提醒、付款申请审批、待支付、实际付款确认、客户实际回款、发票和项目关闭是不同事实，不能互相替代。
- 客户付款节点只表示合同约定或财务确认条件；未接入客户实际回款台账时，不能声称客户已回款。
- 供应商付款申请审批通过只表示允许支付；只有财务实际付款确认才计入已付款。失败、撤回、冲正或退款必须按独立记录和有符号金额核对，不能覆盖原付款。
- 收入、成本、利润、含税口径、工时计价、费用分摊和占用资金公式必须经财务适配确认；不要用回款金额替代收入，也不要用报价成本替代实际成本。
- 合同替代、追加或变更后，必须按有效合同金额和历史收付款关系核对，避免重复累计。替代节点的历史分配已经占用收付款额度；旧合同付款申请保留审批历史，不等于仍可继续支付，须检查 `payment_execution_eligible`，未知不能当作可支付。冲正卡中的当前合同分配影响来自原付款的明确关联，批准后追加反向分配；审批期间关联变化须重新核对和审批，不覆盖原分配。
- `finance_handoff.formal_start_materials` 是财务从正式开工流程取得的冻结订单/合同关联材料；`contract_follow_up` 的逾期状态只用于催补，不能当成合同已收到。
- `mold_transfer_receipts.move_time` 来自客户签收日期，由财务人工确认；客户签收与 `CustomerAcceptanceRecord` 质量验收是不同事实，不能因为登记移模时间就声称验收通过。
- `quality_finance_context` 分别提供有权读取的客户验收影响与供应商扣款责任/结算记录。整改复验通过不抹去历史费用，责任确认不等于已结算，已结算也不等于实际收付款；只沿明确 ID/原单引用追溯，不能按金额或文字相似自动对冲。`visible=false` 表示无权核对，明细截断表示历史未完整返回，均不能解释为没有记录。

默认只做只读上下文核对，不要确认收款、确认付款、生成发票、执行银行转账、建立同义财务总账、导出敏感金额或改写 ERP 财务事实。

当客户收款节点只有条件文字、尚无结构化触发事件、账期或预计到期日时，不要自行解析“DFM 后 15 天”等文本。用户明确要求维护且已提供合同依据时，先用 `query_finance_context` 取得真实项目版本、已生效销售合同和节点 ID，再调用 `prepare_customer_receivable_schedule` 准备确认卡片。本人确认后才能保存；触发日期没有正式依据时保持未触发，不能生成到期或逾期结论。

当用户明确要求登记客户实际回款，且 `query_finance_context` 已返回真实项目、项目版本、已生效销售合同和收款节点时，才能调用 `prepare_customer_receipt_confirmation` 准备确认卡片；该工具只生成 proposal，必须由用户本人核对卡片后才写入客户实际回款台账。

当用户明确要求登记供应商实际付款，且 `query_finance_context` 已返回真实项目、项目版本、已审批供应商付款申请和授权余额时，才能调用 `prepare_supplier_payment_confirmation` 准备确认卡片；该工具只生成 proposal，必须由用户本人核对卡片后才写入实际付款确认记录并扣减授权余额，不执行银行转账。

当用户要求核验合同付款条件或申请供应商付款，先从 `supplier_payment_options` 核对当前生效委外合同、当前材料版本的节点、核验状态及可选付款审批流程。条件尚未核验时，取得用户提供的正式依据后调用 `prepare_supplier_payment_condition`；本人确认只记录核验，不自动申请付款。申请时使用真实节点、项目版本、金额币种、原因和返回的流程 ID 调用 `prepare_supplier_payment_request`；本人确认后占用节点额度并提交 Agent BPM。不要凭模型判断把条件文字当作已核验，也不要将申请提交或审批通过说成已经实付。余额包含其他申请占用、实付与合同替代的历史分配，确认时会重新核对。

原付款申请为草稿、退回、驳回或业务生效阻断且没有实付历史时，可按用户要求使用同一 `prepare_supplier_payment_request` 修订，填写查询返回的 `existing_subject_id`、`subject_revision`、用户说明的 `revision_reason` 以及完整的新申请材料。节点变化须重新核对新节点条件和余额。本人确认后在原申请上增加版本并从头开启完整审批轮，保留旧材料与审批历史；不能另建申请绕过原申请状态，也不能修订审批中、已经生效或有实付历史的申请。

当用户明确要求纠正已确认的供应商付款，先通过 `query_finance_context` 核对原付款 ID、金额币种、原单号、已发生冲正和 `finance_correction_options` 中适用审批流程。取得实际冲回依据、原因及日期后，用 `prepare_finance_correction` 准备全额冲正申请；模型不能自行填写原付款 ID 或选择没有返回的流程。本人确认仅提交 Agent BPM，批准生效才追加反向记录并恢复原授权占用；审批中、驳回、退款执行和冲正生效必须区分。本工具不办理银行退款、客户回款冲回、扣款撤销或 ERP 对账；不要将供应商付款冲正套用到其他记录。项目暂停、终止或关闭后仍可按财务授权办理可审计更正，不恢复普通生产执行。

原冲正申请为草稿、退回、驳回或业务生效阻断时，用户要求修订后重提，应继续使用 `prepare_finance_correction`，填写查询返回的 `existing_subject_id`、`subject_revision` 和用户说明的 `revision_reason`，保持原付款关联并重新提供完整核对材料。确认卡展示原材料与当前分配影响；本人确认后新建审批轮，从头完整重审。旧审批及阻断记录保留，不能把修订当作沿用旧批准直接执行；审批中或已经生效的申请不能这样改写。不要因 CORRECTION_PENDING 改用另一笔付款绕过原申请。

当用户明确要求登记供应商扣款责任或结算依据，且上下文中已有供应商、委外合同或工程联络扣款线索以及正式责任/结算依据时，才能调用 `prepare_supplier_deduction_settlement` 准备确认卡片；该工具只生成 proposal，必须由用户本人核对卡片后才写入供应商扣款责任/结算记录，不执行收付款或自动抵扣。

对已存在的责任确认登记后续结算时，使用查询返回的原记录 ID 作为 `previous_deduction_id`，保持原供应商、合同、联络、责任和金额币种，填写实际结算单号及依据。`source_ref` 留空，原来源通过前次 ID 保留；不能通过换来源编号把同一事项伪装成独立新扣款。可用 `customer_acceptance_id` 明确关联同项目客户验收原件，已有验收关联不得替换或丢弃；该关联只说明问题来源，不等同于客户与供应商扣款金额相等、已抵扣或已收付款。确认会重新核对当前状态；查询中的旧责任记录保留历史，但明确后续结算生效后不再重复计作当前未结算事项。

当用户明确要求按客户签收日期登记移模时间，且已提供真实项目版本、签收日期、签收单号、签收人和依据时，调用 `prepare_mold_transfer_receipt` 准备确认卡片；本人确认后只写入 `MOLD_TRANSFER` 客户签收记录，不创建质量验收、回款、结算或项目关闭结论。
