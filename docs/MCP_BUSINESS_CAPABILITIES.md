# 以业务流为中心的 Skill 与 MCP 能力

2026-09-15。用户要求减少 ERP 式菜单和页面，以部门、业务类别和业务流组织工具及技能，统一从 AI 会话使用，必要审批按需打开右侧工作区。本文区分实际实现与后续工作。

## 目标组织方式

每项能力目录记录业务流名称、业务类别、参与部门（可多选并由管理员维护）、所需工具、资料输入、结果回执、强制人工事项、失败恢复及版本。部门用于分类和参与关系，不是授予权限的捷径，不按部门创建多个 Agent 对话入口。

例如工程联络协作包含发起/历史补录、选择责任部门、分派、过程记录、反馈、必要正式审批、整改复验及关闭；采购业务流可包含资料核对、价格审批、正式下单，按既定归属复用 ERP 业务工具。Skill 编排步骤和证据核对，MCP 暴露受控业务动作，后台事务与权限仍由业务服务执行。

会话中的数据和附件不能修改工具授权或批准规则。需要人员确认时形成绑定材料版本的待确认操作，模型不能自填确认值，也不能直接调用正式批准/执行接口。当前写操作还未全部封装为会话工具，必须持续开发，不能把页面上的按钮视为自动完成该接入。

## 当前协议接入

- MCP 路径：POST /internal/runs/{run_id}/mcp，采用 JSON-RPC 请求及 JSON 响应，支持 initialize、notifications/initialized、ping、tools/list、tools/call。GET 返回 405，未提供服务端 SSE 推送。当前协议固定为 2025-06-18。
- 这是本项目 Harness 使用的私有入口，不是任意第三方客户端的公共 OAuth MCP 服务。请求需要已有 Worker 凭据、任务 URL 和 X-Mold-Run-Epoch；这些由可信 Harness 设置，不暴露给模型参数。身份从持久化 Run 的 user_id 解析，所有调用重新检查用户、权限指纹及租约。
- tools/call 的 params._meta 中 mold/sequence 由 Harness 填入，复用同一 Step 幂等回执；模型参数不能替换用户或执行步骤。旧内部工具入口也复用同一个 execute_step，不建立第二套业务执行代码。
- Harness 经 MCP 发现当前授权的完整工具目录，转换成模型工具定义，由模型判断是否调用；不按用户输入关键词分流。工具结果包含证据 ID 与结构化资料，后续恢复和撤权检查沿用原机制。
- 后端能力目录已为 `/api/capabilities` 和管理员能力分配接口统一返回工具/Skill 的名称、业务类别、部门、类型、人工确认模式和依赖工具；前端优先使用后端元数据，避免把能力分类长期固化在页面代码里。当前仍是代码登记目录，管理员在线维护多部门参与关系、资料输入、结果回执、失败恢复和版本的完整目录尚未完成。
- 查询工具声明只读。工程联络有 query_contact_cases、query_contact_context 及 contact_collaboration_review 技能。列表最多100张可见联络单，每单最近20项任务并附全量计数；详情工具返回当前授权单据资料和可用办理对象。十一项 prepare_contact_* 工具只生成持久化建议，声明 readOnlyHint=false，业务必须另经本人确认。所有同一步骤重试继续复用 Step 回执。
- 尚未完成：业务流和参与部门的完整在线可编辑分类目录、所有业务 Skill、其他业务写入的提议/确认/执行工具、OCR（用户要求暂缓）、公共第三方 MCP 授权及生产部署验收。不把内部受控接入称作通用第三方接入完成。

### 项目主线协调器

- `query_project_lifecycle_context` 是全生命周期只读总入口，只复用下面三个分段协调器的结构化结果，返回当前分段、分段焦点、进度、阻塞、权限缺口和资料矛盾。项目暂停时先建议读取暂停恢复上下文；终止或已有结项清单时进入收尾分段。
- `query_project_kickoff_context` 只读串联承接、销售合同、正式开工与基线计划，合同作为可并行补齐事实，不冒充开工依据。
- `query_project_execution_context` 从基线计划继续串联设计/BOM、采购或整套委外、制造质检、装配试模、交付签收与客户验收。它只返回阶段投影、当前焦点和下一阶段查询能力，不执行 ERP 动作。
- `query_project_completion_context` 从交付验收继续串联发票与客户回款、供应商付款与结算、异常关闭、全过程归档及最终关闭，并严格区分正常关闭与终止结算清单。它不会登记收付款、更新清单或关闭项目。
- 总 Skill 首轮只开放 `query_project_lifecycle_context`，其可选依赖仅为三个分段协调器和暂停恢复协调器；三个分段 Skill 首次激活也各自只开放一个协调工具，阶段专用工具继续作为可选依赖。由此形成“总览 → 分段 → 专用能力”的逐层工具边界，保留多轮 ReAct 轨迹，也避免一次向小模型提供整套业务工具。
- 任何阶段未授权时保持 `UNAVAILABLE`，不能通过其他阶段、历史会话或模型自然语言猜测；整套委外与内部加工分支只按已读取的有效加工方式切换，终止分支的不适用项必须有明确结项清单依据。
- Skill 的激活词、自动激活词、ToolSearch 抑制标记、优先模式和目录路由词由领域包随每次运行上下文显式交给通用 Harness；Harness 不通过业务代码导入成功与否来猜测这些元数据，Worker 重启后同一请求仍保持确定性工具边界。

## 工作区边界

常驻入口仅为会话与消息通知。待审批从消息通知进入；左下角账号菜单→设置统一配置人员权限、工具技能及审批流程。右侧没有常驻模块菜单，仅在打开会话材料或消息明细时显示工作区；标题最右侧仅保留工作区展开/收起按钮。

联络单材料区已进一步改为单张资料只读查看，不再包含发起、部门派发、人员分配、反馈编辑和全部联络单列表；这些业务接口保留，已由联络会话工具提议和必要人工确认承接。查询结果中的材料入口可打开当前单的发起信息、协作进度与过程时间线。已接入原件下载、图片预览、附件历史版本和方案 BPM 实例；材料区可查看真实审批节点。自由协作流程的图形画布尚未实现，现有责任事项和时间线分别反映分派与操作事实。材料区与业务菜单的区别在于只呈现当前任务需要核对的对象，不成为另一套模块操作台。

协议依据：[MCP 传输规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)、[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。这里只实现上述明确子集，未宣称通过所有外部 MCP 客户端认证。


## 已实现的联络建议与确认链

`自然语言任务 → 模型选择查询/准备工具 → MCP 当前用户校验 → Step 保存建议 → 会话展示具体内容 → 本人获取确认凭证 → 再次校验授权/版本/办理资格 → 联络服务 → 同一事务保存业务、回执、审计和 outbox → 当前材料区`

MCP 不提供确认执行工具。POST /api/contact-proposals/{step_id}/intent 只接受已登录本人和 CSRF，依据数据库 Step 读取建议而非相信客户端回传参数；确认沿用 POST /api/human-actions/{intent_id}/confirm。Worker 的 Bearer 凭据不构成人员登录。确认令牌只返回浏览器，不写入模型上下文。GET /api/contact-proposals/{step_id} 返回本人已确认回执，以便刷新恢复卡片状态。

## 项目暂停与恢复建议链

`query_project_control_context` 返回指定项目的执行状态、版本、有效计划、未完成任务、当前暂停区间、客户承诺交期及可选审批模板。`prepare_project_pause` 与 `prepare_project_resume` 只保存建议证据；登录本人通过 `/api/project-control-proposals/{step_id}/intent` 核对后，确认动作在同一事务中创建暂停/恢复单并提交 Agent BPM。回执状态为 `SUBMITTED`，不表示审批已生效。

暂停审批冻结当前有效计划的全部未完成任务。恢复按同一暂停区间计算实际天数并保存每个节点顺延前后值；客户承诺交期不自动变化。计划、任务、流程、项目版本或授权变化会使旧建议失效。该能力不新增菜单页面，不调用 ERP 审批流；真实 ERP 项目状态仍待适配联调。

## 项目终止、结算与关闭建议链

`query_project_closure_context` 返回项目状态、关闭模式、清单、修订历史和实时阻断项。`prepare_project_closure_checklist` 建立正常关闭清单；`prepare_project_termination`、`prepare_project_normal_close`、`prepare_project_settlement_close` 分别准备终止、正常关闭和终止结算关闭的审批材料；`prepare_project_closure_item` 准备单项核对记录。所有建议绑定项目、清单及材料版本。

终止和最终关闭经本人确认后只提交 Agent BPM，审批生效时再次检查状态与清单；单项清单确认直接追加带人员、依据、来源和时点的修订记录。来自 ERP 的事实必须附 ERP 原生引用与截至时间，不能由模型把摘要冒充执行回执。终止只停止 Agent 本地未完成计划任务，不复制或改写 ERP 任务、采购、在制品及财务台账。

正常关闭和终止关闭使用不同清单。不适用的交付或验收只在终止清单中按规则填写原因；正常项目仍须交付、适用验收、发票、回款、供应商结算、异常处理和归档均完成。最终关闭前动态复核本地计划、联络事项、付款占用和 Agent 本地采购，过期事实会阻断旧申请。

每张建议绑定用户权限版本/指纹、所属任务、真实资源标识、材料版本及展示摘要；发生取消、撤权、版本或部门/人员资料变化时重新准备。同一次建议的幂等操作标识由服务端生成，模型不能指定。时间线仍是协作记录，不能代替正式审批、验收和关闭。

## 项目业务档案核对

`query_project_dossier` 是只读汇总工具，可用项目 ID，或项目编号/名称、模具号、工程联络资料、采购订单编号、业务单据编号、合同编号等当前可见线索反查项目。它同时要求 `project.read` 与 `project.dossier.read`，并且每类反向线索还要具备相应查询工具及业务读取权限；字段被裁剪时不会用隐藏字段反查。

返回内容包括项目卡片、项目画像、模具、当前有效计划摘要、工程联络协作、采购订单、各类本地业务记录、供应商实际付款确认汇总和销售合同付款节点。资料覆盖范围由 `coverage` 与 `limitations` 明示；没有分配工具或达到上限时不得解释为业务不存在。该工具不生成新菜单，不写 ERP，也不把 ERP 中采购、制造、财务原生台账复制进 Agent。

当同一编号命中多个可见项目时返回 `AMBIGUOUS` 候选，模型必须请用户指定项目 ID 后再继续。`risk_signals` 只代表当前已见的计划逾期、开放联络或供应商上报异常等事实信号，不能直接下整体延期、成本超支或回款完成结论。

## 工程联络结构化影响与执行边界

`query_contact_cases` 与 `query_contact_context` 现在返回联络主数据、责任事项的受影响对象/原生编号、处置动作、交期和金额，以及反馈后的实际时间、工时、金额、证据与来源。`prepare_contact_create`、`prepare_contact_task`、`prepare_contact_response` 要求同样的结构化材料；引用 ERP 事实时必须带 `source_ref` 与 `source_as_of`，不能用自然语言摘要替代原系统回执。

处理方案审批冻结上述影响材料及当前附件版本。审批生效仅写入幂等的方案交接记录并通知有权读取的责任人和部门负责人；图纸、物料、采购单、在制任务、供应商任务、节点或合同仍由各自业务工具执行并取得权威回执。实际办理反馈只追加，不覆盖旧版本；独立复验和人工关闭继续与方案批准分离。

模型工具循环保留通用语义选择，不按关键词分流。系统提示要求所问字段齐全后停止扩展查询，运行时在已有证据且工具轮数或上下文达到保护阈值时进入只输出收口轮，防止小模型反复查询无关业务直至预算耗尽。收口轮不新增事实，只能引用本次已取得的证据 ID。
