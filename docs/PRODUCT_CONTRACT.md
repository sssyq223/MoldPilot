# 产品开发约束

本项目是 WorkBuddy 形式的智能体，核心为 Agent + Harness + LLM + Tool + Skills。不是传统 ERP，不是给后台管理系统附加聊天窗口。

统一 AI 会话负责用户目标、可展示计划、Skill 选择、真实工具执行、证据、补充信息、人工等待、取消、恢复和结果。右侧可收展工作区承载共享业务资料与人工操作；左侧只承载会话与通知。业务能力由受控后端提供，人员和 Agent 受同一业务授权约束，人工入口与 Agent 凭据分离。

2026-09-15 用户再次明确：开发重点是业务功能和业务流，并封装为 Skill 与 MCP 工具；不要每新增业务就新增菜单、按钮和独立页面。普通查询、整理、发起及流转优先通过统一会话完成，必要审批才按需打开右侧材料/确认工作区；管理员权限与流程配置保留必要界面。现有业务组件是可复用的按需工作区，不作为常驻 ERP 模块导航；缺少工具封装或人工确认接入时必须标为未完成，不能只隐藏菜单就宣称 Agent 化完成。

工具与 Skill 按部门、业务类别及业务流组织。每条业务流包含所需操作、资料、前置校验、角色参与、人工决定、结果回执与异常恢复；MCP 工具封装可执行的受控业务动作，Skill 组织该业务流的步骤与核对要求。同一流程可跨部门、复用多个工具；部门归类不创建多个 AI 身份入口，也不自动授予权限。管理员可以跨部门给用户增加业务能力，最终以业务权限、数据范围、工具授权及强制人工规则的交集为准。已有 ERP 能力经受控工具复用，Agent 缺少的业务自行实现，不重写旧 ERP 审批流。

所有新增开发须回答：该能力如何在统一任务入口使用、需要哪些工具/Skill、如何展示证据与等待、如何进行范围隔离、如何恢复，以及哪些决定必须由人确认。人工办理独立可用，不代表把产品改为传统 ERP。

依据：需求说明书 V1.1、技术文档 V3.6 与本会话最新约定。最新明确约定优先；旧 Tool/Skill 不复用。ERP 源码和 SQL 作为关联参考，不迁移、修复或开发旧系统，不复制 ERP 实时台账。

完整开发范围是 V1.1 的 FR-001～118 及 V3.6 全部适用要求，聊天中列举的模块仅为示例，不构成缩减后的开发清单。用户明确报价、中标、合同上传及项目大节点维护均在 Agent 项目开发：包括各自的业务表单、资料及版本、状态流转、权限、BPM 审批、查询追溯与业务衔接。ERP 有客户、合同或项目节点等基础表/接口，不代表上述流程已经实现，也不能据此取消 Agent 开发项。逐条覆盖见 REQUIREMENTS_TRACEABILITY.md 及 requirements/coverage.json；未形成验收证据的条目保持未验收。

2026-09-14 用户明确：开发每项业务前先检查 ERP 已有实现。已有业务通过新受控适配器复用现有 ERP 接口，正式操作必须由用户人工确认。此授权允许业务 API 改变 ERP 事实，不允许 Agent 直写 ERP 数据库，也不允许修改 ERP 源码。

采购范围：原材、五金、委外属于 ERP 已有能力，不得在 Agent 重做；Agent 新增辅材、办公用品、试模料采购。办公用品支持部门/费用归属，不能强制绑定模具项目；试模料须核对客户供料并由设计、项目确认额外采购需求。其他业务按 ERP_SCOPE_AUDIT.md 的逐项核对结果决定复用或补缺。

具体动作按能力归属执行：采购下单、拆单等 ERP 已有业务功能由新受控适配器调用，不因其出现在 Agent 审批过程中而重新开发。用户明确缺少的辅材、办公用品采购、发货车辆及物流信息维护由 Agent 新开发，试模料采购继续保留。新增采购若能安全复用已有通用下单/拆单能力，先核对接口支持的类别和业务规则；不能在两侧各生成一份订单。接口和对象归属在能力目录中明确绑定，不能根据“本地查不到”临时切换来源。

钢料两种路径已明确：拆单与整单不拆均按现有 ERP 业务执行，保留 ERP 内置的业务路由及后续处理，不重新开发、不强制拆成只保存分组接口，也不以不能关闭 autoRoute 判定业务不可复用。人工确认需展示选定路径及其实际业务影响，授权范围包括该已确认 ERP 路径的既有业务处理；Agent 跟踪业务回执。ERP 业务路由不等于本项目 BPM；审批、异常及工程联络单仍按本项目已确认归属处理。

合同会话上传流程已确认：原件上传→OCR 解析→保存草稿及字段来源→上传人核对→正式发起 BPM。普通审批节点后续可在管理员政策、用户明确委托及本人当前席位权限同时满足时由 Agent 代办；强制人工节点持续受保护。不能以 OCR 识别结果直接形成正式合同审批快照，不能把一般工具许可视为审批委托。

审批系统单独归属 Agent：只参考 ERP 部分业务的审批顺序与规则，不调用 ERP 的审批流、待办、发起审批或审批决定接口。Agent 自建完整 BPM，支持灵活配置节点、人员、条件、必须驳回规则、模板发布版本、重复调用、材料快照、审批历史与运行恢复；适用于三类新增采购和接入 ERP 业务的审批需求，不能缩减为只对新增单据审批。

通用 BPM 建成后，由管理员配置业务模板来实现新模/改模设计上传审批、采购价格审批等流程；不是每个业务单独编写一个审批引擎。模板绑定业务表单和版本、人员解析规则、节点条件及批准后的受控业务动作。保存草稿、校验、发布、复用分别管理；已启动实例固定其发布版本，人员在办理时仍须校验当前权限。配置审批人员不等于授予业务权限，管理员授权与实例参与资格必须同时满足。

异常与工程联络单归属 Agent 新开发，不能因 ERP 已有异常代码而改为调用旧异常处理流程。工程联络单是解决异常的业务载体，依据 FR-082～090 实现问题上报、方案评估、影响清单、必要的人工审批、整改落实、复检/复验及人工关闭；同时覆盖需求规定的客户设变与改善事项。2026-09-15 用户明确：处理过程不固定，不要求管理员预配置；支持手写材料上传识别核对，以及发起人选择责任部门、组织处理或线下讨论线上记录。协作过程与正式审批分开，详见 ENGINEERING_CONTACT_COLLABORATION.md。引用 ERP 原始业务对象和证据，获批后的相关业务执行才通过获准的 ERP 业务接口办理。方案获批不等于整改完成或异常关闭，缺少必要执行与复验结果不得关闭。

审批配置与异常闭环的具体开发约束见 BPM_AND_EXCEPTION_CONTRACT.md。设计上传、新模/改模及价格审批可作为通用引擎的配置验收场景，具体人员、金额阈值和分支规则由管理员设置，测试样例不作为生产制度。

ERP 复用范围为既有业务查询和执行。Agent BPM 审批事实与 ERP 业务执行事实分别保留；审批通过不等于 ERP 操作成功。若现有业务接口硬性依赖 ERP 原审批状态，单独记录接口适配缺口，不能暗中调用旧审批、直接改 ERP 库、修改 ERP 源码或伪造执行成功。正式动作仍需独立人工确认，LLM 不持有可代交确认凭据。

技术文档中与最新确认相冲突的“ERP 只读、不执行接口”“全部业务在 Agent 重建”，以及早期审查中“ERP 单据沿用原审批”等均不再作为实现依据。

交付状态必须区分实现、自动化测试、真实模型验证、部署验证和业务验收；不把视觉概念或模拟输出当成真实 Agent 能力。未完成项在 DEVELOPMENT_STATUS.md 登记，全部业务需求继续保留，不按功能划分产品阶段。

2026-09-14 联调安排：用户明确先继续开发，待后续真实测试时由用户启动 ERP，再一起做联调。现在依据源码、接口契约和合成数据开展开发及模拟验证；不要求用户提前启动 ERP，不把暂未联调当作停止 Agent 开发的理由。模拟通过与真实 ERP 联调通过分别记录，实际 ERP 写入测试到联调时按确认的测试环境办理。
# 模型意图与工具调用约定（2026-09-14）

不按寒暄固定词、是否出现“查询”等关键词分流输入。模型根据完整输入和可用上下文理解意图，自主决定直接回答、澄清或调用工具；混合寒暄与业务请求也按完整语义处理。Harness 校验授权、参数、执行回执与证据，不以关键词替模型判断意图。这里的 ReAct 是智能体执行模式，前端技术栈仍为 Vue3。

本项目保留当前用户完整的已授权工具目录；权限过滤是安全边界，不是按输入猜测后裁剪能力。不得为掩盖模型接口超时而增加固定词分流或默认削减工具目录。内网 30B 的完整目录对照测试已通过，公网超时继续按访问链路问题定位。
