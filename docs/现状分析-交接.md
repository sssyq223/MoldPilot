## 一、项目定位

MoldPilot 是面向模具项目协作场景的 Agent 智能工作台，目标是将以下能力集中到一个 Web 工作区：

- Agent 对话与任务执行
- 受控工具调用
- 人工确认与审批
- 项目生命周期协作
- 文件和业务证据留存
- 操作审计与可追溯
- ERP 只读事实接入

当前准确定位不是生产级 ERP，也不是已经完成全生命周期闭环的产品，而是：

> **具备较完整 Agent 安全控制和模具业务原型能力、正在进行真实 ERP 联调和核心业务闭环验证的内部开发/业务验证系统。**

适合：本地开发、内部试用、业务流程验证、交互原型迭代。

暂不适合：直接生产上线、替代 ERP、对外承诺全生命周期自动化。

代码规模已经较大：

- `backend` 约 350 个文件

- `tests` 约 89 个文件
- 另有脚本、文档、迁移和本地运行配置

## 三、已经具备的能力

### 3.1 Agent 与安全控制

项目已经具备比较成熟的 Agent 控制思路：

- 工具权限和工具激活范围
- 人工确认
- Proposal / Confirmation
- BPM 审批
- 业务版本冻结
- 证据链和操作审计

- `SCOPE_CLOSED`

这部分是项目最有价值的资产。后续优化应优先保护这些安全边界，不能为了“让 Agent 更自动”而绕过确认和事实来源约束。

### 3.2 模具业务覆盖

当前已经涉及较多模具项目生命周期能力：

- 报价接收和报价版本
- 中标接收
- 合同
- 项目启动
- 正式开工
- 基线计划
- 设计进度
- 采购
- 制造
- 装配
- 试模
- 出厂放行
- 发运
- 客户签收
- 客户验收
- 财务付款条件
- 供应商付款与扣款
- 工程变更
- 项目暂停/恢复
- 项目结项
- 文件附件和审计证据

### 3.3 业务事实边界

项目已经明确区分以下事实，方向正确：

- Agent 本地事实不等于 ERP 事实
- ERP 有履约记录不等于客户已签收
- 客户签收不等于质量验收
- 付款记录不等于回款完成
- 有计划不等于计划已生效
- 项目状态 ACTIVE 不等于正式开工已生效
- 试模通过不等于允许发运
- 基线计划不能绕过正式开工

这类业务语义边界必须继续保留，并应逐步由后端状态机和数据库约束承载，而不是主要依赖模型理解。

### 4.1 已完成或基本成形

- 前后端基础架构
- Agent 会话和任务执行框架
- 工具调用与人工确认机制
- 审批、审计、证据相关模型和接口
- 模具领域业务包的大量流程能力
- ERP 只读适配的一部分
- 本地开发和浏览器交互原型
- 较完整的需求追踪、开发状态和验收文档

### 4.2 仍未形成真实闭环

当前最关键的阻塞集中在真实 ERP 交接链路：

- `BROWSER-BID-START-001` 仍处于 `DRAFT`
- 没有生效的正式开工通知
- 没有生效的基线计划
- ERP 已返回 `M260133 / M260133-P3` 候选，但 Agent 侧尚未形成业务负责人确认的项目映射和模具交接
- Agent 项目与 ERP 项目的明确映射仍需业务确认
- 启动交接无法进入稳定的真实业务闭环

因此目前系统更擅长回答：

> 为什么当前不能继续、缺少什么前置条件、哪些事实尚未确认。

但还不能证明：

> 从报价到开工、执行、交付、财务收尾能够在真实 ERP 数据和真实角色参与下完整、可重复地跑通。

### 4.3 ERP 接入的当前定位

ERP 当前主要作为只读事实源，涉及或计划涉及：

- 项目和模具
- 工单、报工和工序
- 采购、入库、库存
- 质检
- 履约
- 付款

这个只读策略在安全上是正确的，但产品上仍主要是：

> Agent 工作台 + ERP 事实查询 + 本地审批/证据层

还不是完整的 ERP 协同执行层。

## 五、当前最大问题

### 5.1 铺得过宽，核心路径收口不足

业务域覆盖已经很广，但真实业务闭环只有部分被验证。继续增加模块会进一步放大状态组合、权限和维护复杂度。

优先级不应是“再做一个业务模块”，而应是“把一条黄金路径在真实数据上跑通”。

### 5.2 工作区变更面较大，但垃圾文件已隔离

当前 Git 状态仍包含一批跨 Agent Core、API、配置、ERP 业务包、迁移、测试和文档的正式修改，以及部分新增领域代码；这些变更尚未拆成最终提交组，后续仍需按功能边界审查和收口。

本轮已完成垃圾文件治理：`.gitignore` 已覆盖 `.pi/`、缓存、临时目录、日志、测试产物、Office 临时文件和 `*.xls/ *.xlsx/ *.xlsm/ *.xlsb/ *.xltx`；已跟踪文件扫描未发现 Excel、日志、临时文件或备份文件。`.env`、本地数据库目录和运行产物均不进入提交候选。

剩余风险是正式修改尚未分组提交，而不是缓存或 Excel 混入。迁移、代码、测试和文档仍需在每个阶段验证后再拆分成可审查提交；不应通过批量删除或强制清理未跟踪源代码来“收口”。

### 5.3 复杂度已经接近维护风险区

`harness.py`、工具网关、生命周期工具、业务协调器都比较复杂。系统大量依靠 scope boundary、工具激活控制和状态组合来防止 Agent 越权，说明编排复杂度正在升高。

后续应减少模型承担的流程判断，把关键流程迁移到：

- 明确的后端状态机
- 小而稳定的领域能力包
- 结构化 handoff 对象
- 数据库约束
- 固定阶段入口
- 幂等的命令接口

### 5.4 文档完成度可能高于实际产品完成度

项目文档详细，且有许多“已完成”“验证通过”的记录，但文档同时也承认很多需求尚未经过真实 ERP、客户、供应商、财务和现场回执验收。

因此不能只用以下指标判断完成度：

- 测试数量
- 页面能否打开
- 本地浏览器是否通过
- 文档中已完成条目数量

应增加真实闭环指标：

1. 是否使用真实业务数据
2. 是否有真实角色参与
3. 是否有 ERP 原始凭据
4. 是否可以重复执行
5. 是否可以恢复、重试和回滚
6. 是否具备完整审计链
7. 是否可以在干净环境部署

### 5.5 生产化基础设施尚未就绪

当前明显偏本地开发形态，仍需要后续补齐：

- 正式部署方式
- 数据库迁移与回滚策略
- Redis 消费组恢复和积压处理
- Worker 幂等、重试、死信和故障恢复
- 日志集中化和告警
- 密钥管理
- 权限模型
- 数据备份和恢复演练
- RTO/RPO
- 发布、回滚和版本兼容策略

### P1：只做一条黄金路径

> 报价接收 → 中标承接 → 合同确认 → 正式开工 → 基线计划 → ERP 模具交接

这条链应优先解决：

- 正式开工通知的生效规则

在这条链没有真实跑通前，不要继续扩展制造、试模、发运和财务等后续模块。

### P1：明确三类事实

产品和代码中明确区分：

#### A. ERP 只读事实

如 ERP 项目、模具、工单、质检、采购、履约等。

#### B. Agent 本地事实

如报价版本、人工确认、审批、附件、放行依据、客户签收登记、审计记录等。

#### C. ERP 写入动作

目前原则上仍需谨慎设计。所有可能影响 ERP 业务状态的写入，必须单独定义权限、确认、幂等、失败补偿和审计规则。

### P2：降低 Agent 编排复杂度

建议：

- 每个阶段只暴露少量工具
- 工具只负责一个明确业务动作
- 用结构化对象传递阶段结果
- 用后端状态机限制非法跳转
- 对关键命令采用幂等键
- 将校验、授权、业务状态变更放在后端
- 模型只负责理解意图、补充参数和解释结果
- 不让模型决定关键状态是否生效

## 七、建议的验收标准

- 正式开工状态有明确来源和证据
- 基线计划可创建、冻结、查询和审计
- 任意一步失败都有明确阻塞原因

- 新环境可以按文档启动
- 代码、迁移、测试和文档可以作为一个完整版本交付

## 十、最终判断

MoldPilot 的方向是正确的，业务理解和 Agent 安全边界明显强于普通 Demo；但当前最大问题是功能铺得太开、工作区没有收口、真实 ERP 黄金路径尚未跑通、生产化能力尚未形成。

完成这一步后，再根据真实使用反馈决定哪些后续能力值得继续开发。
